# native/ — нативное ядро детектора (C++17, SIMD)

Тот же алгоритм, что в [`detector/`](../detector/), переписанный на C++ без OpenCV. На одном масштабе
(`scales = 1`) кандидаты совпадают с Python-версией бит в бит (проверка: `python/compare_with_python.py`).
Сверх прототипа: поиск крупных целей на уменьшенных копиях кадра, учёт движения камеры, трекер с
прогнозом (фильтр Калмана) и удержанием захвата.

## Что внутри

| Часть | Файлы | Что делает |
|---|---|---|
| Детектор | `src/detector.cpp`, `src/backend_cpu.cpp` | пулинг 2x2, морфологическое закрытие линиями в 4 направлениях, статистика тайлов 32x32, выбор кандидатов, авто-маска неба |
| Ядра SIMD | `src/kernels_*.cpp`, `src/simd.hpp`, `src/kernels_impl.hpp` | один шаблонный код под AVX2 (256 бит), SSE2 и NEON (128 бит) и скалярный эталон; набор выбирается при запуске по CPU |
| Потоки | `src/thread_pool.cpp` | кадр режется на блоки тайлов, блоки раздаются потокам; можно закрепить потоки за ядрами |
| Масштабы | `src/detector.cpp` | `scales` 2–4: тот же поиск на кадре, уменьшенном в 2, 4, 8 раз (min/max-пулинг) — цели до ~28, ~56, ~112 пикс. вместо ~7 |
| Движение камеры | `src/motion.cpp` | сдвиг картинки между кадрами: пирамида градиентов ~300 пикс., поиск минимума разности, субпиксель; ~1–2 мс |
| Трекер | `src/tracker.cpp` | фильтр Калмана (позиция + скорость), прогноз с учётом сдвига камеры, окно поиска по неопределённости прогноза, удержание трека и захвата на пропусках; классы дрон / птица / статичная помеха; одиночные отклики — шум |
| API | `include/dronolok/detector.hpp`, `include/dronolok/dronolok.h` | C++ и C (для Python/ctypes и других языков) |
| Инструменты | `tools/dronolok_bench.cpp`, `tests/test_kernels.cpp` | замеры, качество по разметке, сверка SIMD со скалярным кодом |

Почему так быстро: кадр обрабатывается полосами по нескольку строк, и все промежуточные данные (пулинг,
4 направления дилатации) живут в кольцевых буферах, которые помещаются в кэш L1/L2. В OpenCV каждый шаг
проходит по всему кадру 16 Мп и упирается в память. Плюс полностью замаскированные тайлы (лес, земля)
не считаются вовсе.

## Скорость, кадр 4608x3456 (16 Мп), мс на кадр

ПК: Xeon 2.8 ГГц, 4 vCPU (виртуалка). Python — `detector/` с OpenCV.

| Вариант | 1 поток | 4 потока |
|---|---:|---:|
| Python + OpenCV | 55–70 | 18–22 |
| нативное, скалярный код | 300 | 80 |
| нативное, SSE2 (128 бит, как NEON) | 15–20 | 4.5–6 |
| нативное, AVX2 (256 бит) | 10 | 3.5–4 |

Для Raspberry Pi ориентир — строка SSE2: NEON той же ширины. Ядра Cortex-A76 (Pi 5) примерно в 2–3 раза
медленнее ядра этого ПК, Cortex-A53 (Pi 3) ещё в 3–4 раза медленнее. Точные цифры даст `dronolok_bench`
на самом устройстве.

Оценка поворота камеры: `dronolok_bench кадры.y4m --motion` (по соседнему кадру) и `--motion-long` (сдвиг от
кадра ~1/15 с назад — так приложение считает от 22.5 к/с) печатают строку «оценка поворота камеры, мс». На этом
ПК (1 поток) 0.60–0.63 и 0.63–0.67 мс на кадр: длинная база считается первой, по соседнему кадру — только
когда её нет (начало ролика, сброс), поэтому почти бесплатна (раньше считались обе, 1.1 мс).

## Сборка

Нужны CMake 3.16+ и компилятор C++17 (GCC, Clang или MSVC).

```sh
cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build -j
native/build/test_kernels           # все SIMD-варианты совпадают со скалярным кодом
```

### Raspberry Pi

На самой Pi (Raspberry Pi OS, 64 или 32 бит) — те же команды. NEON включается автоматически.

Кросс-компиляция с ПК на Linux:

```sh
sudo apt install g++-aarch64-linux-gnu      # Pi 3/4/5 с 64-битной ОС
cmake -S native -B build-pi -DCMAKE_TOOLCHAIN_FILE=$PWD/native/cmake/aarch64-linux-gnu.cmake
cmake --build build-pi -j
# для 32-битной ОС: g++-arm-linux-gnueabihf и native/cmake/arm-linux-gnueabihf.cmake
```

Готовые сборки для Pi и Windows собирает GitHub Actions (`.github/workflows/build.yml`), они лежат в
артефактах запуска.

### Windows

Из Linux: `-DCMAKE_TOOLCHAIN_FILE=$PWD/native/cmake/mingw-w64-x86_64.cmake` (пакет `mingw-w64`).
На Windows: Visual Studio 2022, `cmake -S native -B build` и `cmake --build build --config Release`.

## Прогноз и захват

Трек хранит позицию и скорость цели относительно сцены (фильтр Калмана с постоянной скоростью). На каждом
кадре:

1. `GlobalMotion` оценивает, на сколько сдвинулась вся картинка (камера в руке); прогноз трека = прошлая
   позиция + скорость + сдвиг камеры.
2. Цель ищется в круге вокруг прогноза. Радиус — 4 сигмы ошибки прогноза: у молодого трека и после
   пропусков окно шире, у устойчиво летящей цели — уже (меньше шансов перескочить на соседнюю помеху).
3. Если цель не нашлась (слилась с фоном, ушла за провод), трек идёт по прогнозу до `max_miss` кадров.
   Новые и стоящие на месте треки так не держатся — иначе каждый блик оставлял бы «призрака».
4. Захват — самая весомая цель (контраст, число попаданий, не помеха). Он держится, пока трек жив, и
   переходит на другую цель, только если та весомее в `lock_switch` раз в большинстве из последних
  `lock_dwell` кадров (12 при 25 к/с, ~0.5 с; счёт с утечкой). Потерянный захват сначала ищется
   у прогноза и у последней известной точки. Претендент, на несколько кадров пропавший из выдачи (на
   прогнозе, но жив), набранный счёт не теряет (`lock_dwell_keep`): раньше счёт обнулялся, и дрон,
   которого ведёт камера, на 60 к/с пропадавший на 2–4 кадра из каждых 10–15, перевеса в 29 кадров не
   набирал никогда — захват 2 с держал второй самолёт (wt17 с `lock_mover`: на дроне 72 → 86%). Мягкий
   захват на «птице» уступает «дрону» без выдержки (`lock_bird_yield`): новый захват садился на
   пролетевшую птицу раньше, чем дрон набирал попаданий, и выдержка держала его там секунду. 14 к/с
   (4 фазы): на дроне 86 → 87%, ложный 12.6 → 11.6% (wt13 76 → 85%, wt17 80 → 83%); 60 к/с без изменений.

5. **Память статичных помех** (неподвижная камера): места, где цели раз за разом появляются и никуда не
   летят (катушки и изоляторы ЛЭП, фонари), копят такие отклики. Набрав `static_hits` с забыванием за
   `static_frames` кадров, место перестаёт рождать цели; летящий через него трек не теряется.
   `Tracker::saveStatic/loadStatic` — чтобы после перезапуска не учиться заново. Синтетика 4 Мп с
   мерцающими катушками (`synth_sky.py --insulators 12`): ложных треков 2.1 → 0.3 на кадр, с сохранённой
   памятью 0.13; на синтетике 16 Мп 1.7 → 0.07; полнота та же.

6. **Зоны кадра** (`DetectorConfig::zones`): по тайлам основного масштаба — земля (крупные связные области
   текстуры: кроны, дома, край виньетки), небо и смешанные (небо рядом с землёй). Цель, родившаяся в
   смешанной зоне, выдаётся, только когда полетела. Считается каждый кадр, поэтому работает и при съёмке
   с рук. Ролики пользователя, целей на кадре (ложных в основном): большой дрон над домами 9.6 → 3.6,
   перехватчик над снегом 39.8 → 29.3 (ложные цели на ровном снегу зоны не убирают), дрон до взрыва
   5.0 → 4.6; захват тот же, синтетика 16 Мп без изменений.
   В кадрах между полными просмотрами (`full_every`, жёсткий захват — 5 кадров из 6) посчитаны только тайлы
   вокруг треков, и раньше зоны в такой кадр почти целиком становились небом — на экране земля мигала
   (wt18 при повороте камеры: 41 смена тайла за кадр). Теперь такие кадры берут зоны последнего полного
   (2 смены за кадр), захват тот же. `zone_vote` (выкл.): земля по нескольким кадрам — ещё меньше
   мигания и ложных целей на wt15/wt17, но захват на дроне wt18 87 → 83%.
   Тонкое над землёй (`thin_tiles` = 1: столб ЛЭП, мачта, антенна, узкая верхушка ели — ряды земли не
   шире тайла, над которыми земли нет) остаётся землёй, но смешанных тайлов вокруг себя не даёт: раньше
   столб тянул за собой полосу смешанных шириной в три тайла до самого верха. Захват тот же; ложных
   треков wt15 486 → 549, wt17 500 → 552 (там кандидат у верхушки ели больше не обязан лететь).
   Столб с перекладиной шириной в два тайла так не открывается: `thin_tiles` = 2 его открывает, но
   ложных треков wt15 549 → 712.
   Полоса под сеткой (`zone_strip`, вкл.): 1080 строк — это 16 тайлов по 64 и ещё 56 строк, которые в
   сетку не входят. Кроны и столбы у самого нижнего края в зоны не попадали, их верхушки над краем были
   "чистым небом", и захват садился на них. Теперь по последним 64 строкам кадра считается ещё ряд тайлов
   (только для зон, поиска там нет); текстура в нём — земля при любом размере куска, и тайлы над ней
   смешанные. Реальное пасмурное видео 1080p с рук (IMG_3003, без дронов): целей на кадр 3.9 → 0.4,
   захват 90 → 39% кадров (из оставшегося около трети — две настоящие мелкие точки, пролетевшие по
   небу). Ролики с разметкой без изменений (wt15 ложных на кадр 17.2 → 15.6). Цена — 1/16 кадра 1080p.
   Кайма резкости (`halo_k` = 2): камера телефона повышает резкость, и вдоль тёмного столба, мачты,
   края фонаря идёт светлая кайма — светлый кандидат прямо у тёмного. Если в 4 пикс. от светлого
   кандидата темнее фона больше чем на 2 его контраста и это тёмное протяжённое (выходит за рамку
   в 20 пикс.), кандидат "у кромки": цель, только когда полетела. Выбрасывать такие кандидаты нельзя:
   на wt19 захват на дроне падал 84 → 56% (другой трек раньше брал захват). IMG_3003: захват 22 → 20%;
   ролики с разметкой — захват на дроне тот же, ложных на кадр wt19 16.8 → 14.0, wt18 6.4 → 5.4,
   wt23 кадров с захватом 29.5 → 24.0.

7. **Порог по шуму** (`DetectorConfig::auto_thr`, по умолчанию выключен; CFAR, как в радарах и ИК-поиске
   малых целей). Шум отклика — медиана среднего отклика по тайлам кадра (лес и цели — меньшинство, медиана
   их не видит), сглаженная по кадрам; порог = `noise_k` x шум в пределах `thr_min`..`thr_max`, порог
   "горячих" пикселей (текстура, маска неба) — тоже от шума. Постоянный `thr = 10` подобран под шум матрицы
   ~2 уровня: на шумной матрице (вечер, высокий ISO) кадр засыпает ложными целями, а маска неба при обучении
   считает всё небо текстурой; на чистой — теряются тусклые дальние цели. Стоит медиана по ~4 тыс. тайлов
   (меньше 0.05 мс на 16 Мп).

8. **Подтверждение по накопленной уверенности** (`TrackerConfig::ev_confirm`, по умолчанию 3; упрощённый
   track-before-detect / последовательный тест отношения правдоподобия). Каждое попадание добавляет
   `margin^2 - 1`, где `margin` — во сколько раз отклик выше порога, пропуск отнимает 1. Трек выдаётся, когда
   выполнено прежнее "3 из 5" и набрано 3. Шумовые отклики у самого порога, случайно совпавшие 3 раза, больше
   не становятся целями; контрастная цель подтверждается так же быстро, как раньше, тусклая — на несколько
   кадров позже. Кандидаты не от `Detector` (через C API без `margin`) подтверждаются по-старому.

9. **Силуэт крупной цели** (`measure_silhouette`, `TrackerConfig::silhouette`, по умолчанию вкл.). У
   крупного БПЛА (100–400 пикс.) детектор точечных целей находит части: кончик крыла, хвост, подвес, — и
   захват цеплялся за одну из них. Вокруг прогноза захваченной цели (`Tracker::lockSearch`) берётся окно,
   уменьшенное до сетки не больше ~97x97 ячеек; фон и шум — по рамке окна, цель — связная область темнее
   (светлее) фона, расширенная на ячейку, чтобы тонкое крыло не рвало силуэт. Упирается в край окна — окно
   вдвое больше, до `silh_max` (больше — это земля или облако, не цель). Центр и габарит силуэта идут в
   трекер как измерение захваченной цели (`Tracker::setLockSilhouette`); части внутри габарита не рождают
   своих целей и не считаются помехой. Доли миллисекунды на кадр.

10. **Жёсткий захват** (`hard_lock`, `verify_frames` = 10, `hard_miss` = 60, `hard_full_every` = 6).
    Захваченная цель `verify_frames` обработанных кадров подряд классифицируется как дрон и уже пролетела
    по сцене — `LockState::Hard`: захват не переходит на другие цели, держится на прогнозе `hard_miss`
    кадров, детектор смотрит вокруг дрона (`Tracker::roi` только по нему), весь кадр — раз в
    `hard_full_every` кадров. Снимается, если цель оказалась наложением на кадр или уверенно птицей
    (`birdScore` > 0.8). Наложения на кадр (надписи записи экрана): позиция в кадре стоит на месте
    (СКО < `overlay_px` за `overlay_hits` попаданий), пока сцена смещается больше `overlay_cam`.
    Цель на мачте (`anchor_check`, по умолчанию вкл.): у силуэта захваченной цели ищется длинная тонкая
    линия вверх или вниз — мачта прожектора, столб, ствол (`Silhouette::attached`: линия от края силуэта
    длиннее цели в 2.5 раза, или узкий участок внутри силуэта длиннее ширины головы; линия, ушедшая за
    край кадра, засчитывается по пройденному; силуэт, обрезанный низом кадра, — всегда на опоре: верхушка
    столба или кроны над самым краем; на IMG_3003 само по себе жёсткий захват 10 → 5%; силуэт крупнее
    `silh_max`, дошедший до низа кадра, — тоже: мачта с проводами, IMG_3003 захват 28 → 22%). В большинстве из
    первых 4+ замеров есть мачта — цель помеха, захват снимается. При съёмке с рук прожектор «летает» по
    кадру из-за неточной оценки поворота и проходил проверку на дрона: на ролике с перехватчиком захват
    сидел на прожекторе 243 кадра из 244, стало 31 (каждый новый трек на нём отпускается за 4 кадра).

    **Ожидание размера** (`size_predict`, по умолчанию вкл.): размер силуэта захваченной цели ведётся
    альфа-бета фильтром по логарифму — сам размер и скорость его изменения (`Track::ls/dls`,
    `Track::expectedSize()`), то есть приближается цель или удаляется. Детектор вокруг захвата смотрит на
    масштабе ожидаемого размера; силуэт больше ожидаемого в `size_tol` раз (слился с облаком, кроной) не
    принимается; меньший принимается, но в размер не идёт (крыло слилось с небом). Без замеров ожидание
    не экстраполируется: так оно расходилось с целью. Синтетика «крупный дрон пролетает мимо камеры»
    (62 → 400 → 62 пикс., `detector/synth_pass.py`): захват 95% → 98%; на роликах пользователя без изменений.

    **Камера ведёт цель** (`Tracker::setFollowing`, `Tracker::aim`): для камеры на поворотном
    устройстве, которая следует за захватом. `aim()` отдаёт позицию захваченной цели на кадре и её
    скорость по сцене — поворотке достаточно сдвинуть кадр на эту скорость плюс долю отклонения от
    центра. Поворот камеры передаётся в `update()` как `camDx/camDy` (от датчиков поворотки или
    `GlobalMotion`): цель стоит в кадре, а по сцене летит, фон едет навстречу — как доплеровский радар
    отделяет движущуюся цель от неподвижного фона. С `setFollowing(true)` захваченная цель не считается
    наложением на кадр (она и должна стоять в кадре, пока сцена уезжает), иначе захват снимался бы.
    Проверка — «виртуальная поворотка» в тест-приложении (`dronolok_app --follow`): алгоритм видит
    окно в половину кадра, окно поворачивается за проверенным дроном. На роликах пользователя (захват на
    дроне, 2-й проход; было → с поворотной камерой): крупный БПЛА 88% → **99%**, дрон-крыло у берёзы
    56% → **95%**, дальний дрон 40% → 42%, квадрокоптер в облаках 47% → 37–56% (по проходам), тяжёлый
    коптер 81% → 27% — без маски неба (у камеры на поворотке её нет) захватывается ведущий на правой
    половине записи экрана, у настоящей камеры такой вставки нет. Синтетика пролёта: пока цель в поле
    зрения окна, захват 100% кадров; классификатор при ведении увереннее (цель стоит на месте кадра, замеры
    стабильнее): доля «дрон» у захвата и время жёсткого захвата выше.

11. **Пробег цели по медиане**: точка рождения — медиана первых 5 отметок, текущая — последних 5. Одиночный
    скачок (силуэт пересчитал центр, детектор перепрыгнул на соседний отклик) больше не делает из
    неподвижного логотипа «летящую цель».

12. **Оценка движения камеры на записи экрана**: точки, не изменившиеся ни на уровень (наложения, повтор
    кадра), не учитываются; найденный сдвиг проверяется по 16 частям кадра — если за него меньше
    частей, чем вдвое против «сдвига нет», это шевелится что-то в кадре (ветки на ветру) при неподвижной
    камере, и сдвиг 0.

### Камера ведёт цель (запись экрана, поворотка) и очередь целей

Запись игры, где камера сама держит дрон в прицеле (War Thunder wt15–wt19), и съёмка оператором,
ведущим цель. Раньше такой дрон не захватывался: камера поворачивается — маска неба, привязанная к
кадру, «едет» и переучивается со сбросом треков; дрон стоит в кадре и считался наложением или
зависшим (`lock_slow`), а уезжающий фон давал сотни помех.

- **Плавный поворот камеры** (авто на крупном кадре, `Settings::panDetect`): суммарный сдвиг картинки
  за секунду больше 20 пикс./с (по ширине 2560; выход — ниже 8, скачки больше 120 пикс./кадр —
  смена вида, не поворот). Пока камера поворачивается: маски неба нет, ищутся зоны земли, а сдвиг идёт
  в координаты сцены трекера (`Tracker::setSceneShift`) — пробег, скорость и класс считаются по сцене.
  После поворота маска учится заново, но убираются только треки на земле (`dropMasked`).
- **Ведомая цель** (`TrackerConfig::follow_k` = 3, `follow_frac` = 0.3): за последние до 48 попаданий
  камера прошла заметный путь, а цель по кадру — меньше трети этого пути, и она в середине кадра.
  Вес такой цели для захвата ×`follow_k` вместо штрафа медленных; помехой и наложением она не
  становится (и после остановки камеры, `everFollowed`). Ушла из середины или потеряна дольше
  4 кадров — уже не ведомая.
- Прогноз, ушедший за край кадра, новой целью не становится, а захват на нём сразу уступает лучшей
  цели в кадре. Мягкий захват не подхватывает у прогноза мелочь, вчетверо слабее лучшей цели.
- **Сдвиг камеры по кадру 1/15 с назад** (`Settings::motionLong`, `GlobalMotion::setLong`; авто на крупном
  кадре от 22.5 к/с): на 60 к/с плавный поворот сдвигает уменьшенную копию кадра меньше чем на пиксель за
  кадр, и оценка по соседнему кадру занижена в 1.3–3 раза — панорама находилась на секунды позже, ведомый
  дрон по сцене «дёргался» и звался птицей. Сдвиг меряется от кадра round(fps/15) назад, за кадр — его
  доля. 60 к/с: wt19 на дроне 81 → 90% (жёсткий 31 → 88%), wt17 74 → 89%.
- **Дрейф фона** (`drift_min` = 0.25 пикс./кадр при 25 к/с, 0 — выкл.; `drift_tracks` = 5): медленный
  поворот, которого оценка сдвига камеры не видит (прицел игры плывёт ~24 пикс./с — на уменьшенной копии
  меньше пикселя за кадр), — всё неподвижное плывёт по сцене с одной скоростью, а с `lock_slow` такая
  «медленная цель» для захвата весомее летящего дрона. Дрейф — медиана скорости устоявшихся треков за
  ~0.5 с (`drift_obs` = 13 попаданий при 25 к/с, не меньше 8: на 60 к/с 8 попаданий — 0.13 с, шум
  положения отклика того же порядка, что и дрейф), если половина в допуске (½ медианы). Пока он есть,
  пробег и скорость для захвата и проверки — относительно него, плывущее с фоном весит как зависшее.
  При известном сдвиге камеры (`setSceneShift`) не считается. wt16 (захват сидел на верхушке вышки):
  14 к/с на дроне 0 → 98% (фаза 0), 60 к/с 92 → 94%.
- **Жёсткий захват переходит на ведомую цель** (`hard_switch_follow`): условие «претендент вдвое
  медленнее» не для цели, которую ведёт камера, — её скорость по сцене равна скорости поворота. Жёсткий
  захват, севший до того на землю или второй самолёт, держался, пока камера вела дрон (wt17, wt19 на
  30 к/с: на дроне 31 и 60%); без этого на 30 к/с на дроне 84 → 80%. Окно ведомой цели (`follow_min_obs` =
  16 попаданий) — от 30 к/с, ниже во времени, но не меньше 9: на 14 к/с 16 попаданий — уже 1.1 с, и дрон
  получал вес ведомой на полсекунды позже (wt17); на 30 к/с с 9 попаданиями (0.3 с) ведомой
  становилось чужое (wt18 95 → 76%).
- **Отклонение от траектории и по кадру** (`resid_frame`): СКО отклонения для класса «птица» — меньшее из
  посчитанного по сцене и по кадру. По сцене траектория ведомой цели — сумма оценок поворота, их шум
  копится: дрон wt17 на 14 к/с по сцене 2.2–2.6 пикс. (порог 2.2), по кадру 1–1.4. Жёсткий на дроне:
  14 к/с +5 пунктов, 60 к/с без изменений.

## Неподвижная камера над горизонтом

Широкая камера стоит на месте и смотрит на полосу горизонта; дальние дроны — тусклые точки низко над
лесом. Стенд: `detector/synth_horizon.py` (небо с дымкой, облака, качающаяся кромка леса, группы целей
far / high / pair / bird, всё задано в секундах). `dronolok_bench` печатает полноту и задержку
обнаружения по группам и «ложные тревоги» — треки, ни разу не бывшие на цели, в минуту.

- **Трекер в секундах** — `tracker_for_fps(cfg, fps)`: параметры заданы для 25 к/с; СКО ускорения растёт
  как (25/fps)^1.5 (а с ним и ворота по ошибке прогноза), выдержки в кадрах — пропорционально fps, окно
  взмахов не короче 32 кадров. 10 к/с, 30 с: птиц находится 53% → 70%, дронов, принятых за птиц, 1% → 0.
  Полный физический пересчёт (v, v²) находил птиц больше (88%), но 12% попаданий по дронам уходили в
  «птицу». В приложении частота — новые кадры в секунду (повторы записи экрана не в счёт).
  Предел ворот (`gate` = 26 пикс. кадра) по частоте не растёт: раньше он был 40·√(25/fps), и 53 пикс. на
  14 к/с цепляли чужие отклики — верхушки деревьев, второй самолёт (14 к/с, ролики без дронов: кадров с
  захватом −13 пунктов, IMG_3003 −24), а 20·√(25/fps) на 60 к/с (13 пикс.) рвал ведомую цель. Только на
  редких кадрах предел не меньше пути цели за кадр при `gate_pps` = 360 пикс./с (10 к/с — 36 пикс.):
  молодой трек скорости ещё не знает, и быстрая цель уходила за 26 пикс. раньше, чем подтверждалась
  (синтетика горизонта 10 к/с: близкие дроны 91 → 96%, птицы 57 → 70%). На роликах на 10 к/с (3 фазы)
  с ним на дроне 83.8 → 84.4%, жёсткий 71.2 → 70.2%, а на IMG_3003 (с рук, птицы) кадров с захватом
  1.5 → 8.3%: в широких воротах лучше ведутся и птицы. Со всеми правками ночи 30.10
  (PR #29 → сейчас): 14 к/с — близкие дроны 97% (было 97%), ложных тревог 16 → 6 в минуту, птиц
  находится 83 → 78%; 10 к/с — 96% (96%), 8 → 4 в минуту, птиц 78 → 70%; класс «дрон» у дронов 95–96% → 100%.
  Самый медленный взмах (`flap_max_period`, 16 кадров при 25 к/с = 1.56 Гц) тоже в секундах: раньше
  окно периодов было в кадрах, и на 10–15 к/с медленное колебание контраста дрона (облака, поворот
  камеры, ~1 Гц) сходило за взмахи — дрон звался «птицей» и не получал жёсткий захват. Ролики wt13–27
  на 15 к/с (каждый 4-й кадр): «дрон» у попаданий по дрону 69 → 82%, жёсткий на дроне 33 → 43%;
  на 60 к/с без изменений, кроме роликов с повторами кадра (там трекер и так считал меньше 25 к/с).
  Через C API частоту задаёт `dl_tracker_set_fps` (без вызова — 25 к/с).
- **Пробег против пути камеры** (`mover_cam_k` = 0.25): при повороте камеры сдвиг оценивается с ошибкой
  10–20%, и земля, проплывающая через кадр, «летит» по сцене. Летящей цель считается, только если по
  сцене ушла дальше четверти пути камеры за то же время (цель, которую камера ведёт, уходит на весь
  путь, при неподвижной камере условие не действует). wt17 на 15 к/с: захват на дроне 0 → 71% (без этого
  правка взмахов отдавала жёсткий захват траве у низа кадра).
- **Новый захват только на летавший трек** (`lock_mover`; включается сам при камере не быстрее
  `lock_mover_fps` = 31 к/с — `tracker_for_fps`, в C API `dl_tracker_set_fps`): мягкий захват садится на самый
  весомый подтверждённый трек, даже если это первый блик листвы. С `lock_mover` новый захват берёт
  только трек с `cls_min_hits` попаданий, уже летавший по сцене (ведомый камерой и точка спокойного неба —
  сразу). Ролики без дронов, кадров с захватом: 15 к/с 43 → 9%, 60 к/с 26 → 10% (n1 76 → 0); захват на
  дроне 15 к/с 69 → 68%, 60 к/с 83 → 78% (зависший дрон wt15 99 → 78%). Жёсткий захват на роликах без
  дронов и так почти 0 — это про подсветку и выбор цели для узкой камеры. По частоте: на 60 к/с ролики с
  разметкой не изменились, без дронов захват 26 → 23% кадров (n1 и wt22 — запись экрана с повторами
  кадра, там новых кадров меньше 20 в секунду); на 15 к/с — цифры выше. Ночной подбор 30.10: порог 20 →
  31 к/с — на 30 к/с (2 фазы) без дронов 19 → 2% кадров (IMG_3003 23 → 13%), на дроне 87.6 → 86.8%,
  жёсткий 77.3 → 77.6%. На 60 к/с (`lock_mover_fps` 61) без дронов 20 → 4%, но на дроне 89.6 → 87.2%
  (wt15, wt16, wt18, wt24) — там выключен.
- **Жёсткий захват не уходит на «птицу»** (`hard_switch_drone`): переход жёсткого захвата на медленную
  цель (`hard_switch`) — только если она «дрон» без признаков птицы или камера её ведёт (`followed`). На
  15 к/с захват уходил с летящего дрона на медленную птицу рядом (её вес с `lock_slow` в ~5 раз выше):
  wt16 на дроне 12 → 30%, wt18 91 → 97%; ведомая камерой «птица» на 60 к/с wt17 — это и есть дрон.
  **Зависание важнее взмахов** (`hover_first`): зависшая после полёта цель — дрон, даже если её контраст
  качнулся как взмахи (wt18 на 15 к/с «дрон» у попаданий по дрону 72 → 85%).
- **Фон ячейки у кромки** (`bg_near`, по образцу Global Meteor Network: пиксель ярче среднего на K·σ):
  в тайлах неба рядом с землёй ячейка-кандидат должна быть выше своего фона (медиана + `bg_k` СКО), как
  в текстурных тайлах. Кончики веток, заходящие в небо, мерцают в одних и тех же ячейках, и порог у них
  растёт сам. 60 к/с: на дроне 83 → 86%, жёсткий 60 → 64%, ложный 17 → 15% (wt16 72 → 92%); 15 к/с +1%.
- **Скорость после пропуска** (`reupdate`, по образцу OC-SORT; выключено): цель нашлась после 2+ кадров
  на прогнозе — скорость по прямой от последней отметки. 15 к/с на дроне +1%, 60 к/с −1% (wt25 83 → 73%),
  поэтому оставлено ключом.
- **Маска неба в файл** — `saveMask` / `loadMask(path, verify)`: маска сразу закрывает лес, а первые
  verify кадров сверяется с видимым; больше 10% несовпадающих тайлов (камеру сдвинули) — берётся новая
  (`maskReplaced`). Первые 3 с: ложных треков 1.25 → 0.2 на кадр. Приложение кладёт её рядом с видео
  (`.mask.bin`). После сверки маска — новая всегда: из файла берутся только тайлы, закрытые
  доращиванием по помехам (второй слой файла, `DLMASK2`; закрытые так только для светлых — тоже), и их
  перепроверка может открыть снова. Раньше сверка оставляла маску из файла, если она отличалась не
  больше чем на 10%: закрытое прошлой версией программы держалось навсегда (на wt23 с файлом прежней
  сборки к концу ролика — 46 закрытых тайлов неба и 31 закрытый для светлых целей; теперь небо то же,
  что с чистого старта). Файл первой версии читается, но держит маску только до
  конца сверки.
- **Всё ниже горизонта — земля** (`skyline`, по умолчанию): в каждом столбце тайлов маски неба
  кромка — первый сверху текстурный тайл, под которым текстурных больше половины; всё ниже неё
  (гладкая трава, поляна, дорога, просветы между стволами) — земля. Дрон прилетает из-за горизонта
  и бывает над кромкой крон и крыш, ниже неё почти никогда. Облако кромкой не считается (под ним
  чистое небо). Столбец без кромки берёт её у соседей. Кромка не выше просвета в 3 гладких тайла:
  на тёмном небе (War Thunder wt7) яркие облака текстурны, и без этого столбец под облаком до
  самого леса становился землёй — дрон перед облаком не искался (обнаружение 0% → 79%).
- **Маска уточняется по ячейкам** (`fine_mask`, по умолчанию; нужен `bg_map`): тайлы земли 64x64
  рядом с небом считаются бэкендом, и в каждой их ячейке 16x16 копится доля кадров с текстурой
  (листва, ветки; забывание за `fine_frames` = 150 кадров). Ячейка, где текстуры почти нет
  (< `fine_tex` = 5%) и рядом сверху или сбоку в той же строке небо, становится небом и смотрится по
  ячейкам с порогом по её фону, как у кромки. Тайл с найденным небом сам открывает соседей, так что
  уточнение со временем спускается до самых крон, а в одинокий просвет внутри кроны не попадает.
  Меняется маска тайлов — копится заново. Записи War Thunder: маска облегает кроны вместо
  прямоугольников 64x64; на wt4 (маска выучена, пока игра переключала камеру) открылась вся
  ошибочно закрытая полоса неба. Цена — тайлы у кромки считаются: 4 Мп 0.95 → 1.15 мс, 16 Мп
  2.3 → 3.1 мс на кадр (4 потока). Полнота на синтетике горизонта та же.
- **Маска дорастает, где копятся помехи** (`grow_mask`, по умолчанию; `Detector::noteClutter`):
  приложение отдаёт детектору помехи трекера (`Tracker::clutterDets`), пока камера неподвижна.
  Они копятся по ячейкам 16x16 с забыванием за `grow_frames` = 60 кадров; раз в четверть окна
  тайл неба, где помех на кадр в `grow_k` = 3 раза больше среднего по небу этой сцены (и не меньше
  `grow_min` = 0.1) и они хотя бы в `grow_cells` = 2 ячейках, закрывается, если прирастает к
  маске: земля хотя бы с трёх сторон, или с двух и над ним не чистое небо (помех мало и текстура
  реже `grow_sky_tex` = 2% кадров). Края кадра слева, справа и снизу считаются землёй. Так
  закрываются дыры в маске на дальнем поле и траве, а ряд неба над ровной кромкой крон и крыш
  (сосед-земля один — снизу) остаётся открытым; вокруг захваченных целей маска не растёт. Уточнение
  по ячейкам при этом не сбрасывается. Захват на дроне по разметке wt15–19 не изменился; помех на
  кадр к концу ролика: n4 39 → 23, wt16 21 → 18, n6 9 → 6; на wt18 почти все помехи — на верху
  крон, их маска по замыслу не закрывает (103 → 100).

  неба. Раз в `recheck_every` = 10 кадров (если кадр просмотрен целиком) для тайлов, закрытых по своей

- **Облака по цвету** (`sky_color`, по умолчанию; галочка во вкладке «Алгоритм», в мультитесте

- **Лист у камеры — не цель** (`leaf_color` = 8, `leaf_hits` = 2; галочка «Лист у камеры — не цель (по
  цвету)», в мультитесте `leaf_color`, `leaf_hits`, в `--bench` и `dronolok_bench` — `--no-leaf-color`).
  На wt23 (птиц на wt нет) почти все ложные захваты — листья у самой камеры: тёмное пятно в 10–60 пикс.
  пролетает по небу, как дрон, а трекер отстаёт от ускоряющегося листа. По яркости его от дрона не
  отличить, по цвету — можно: листва зелёная, жёлтая, оранжевая, красная или бурая, то есть синего
  меньше яркости или зелёный выше красного и синего — phi = max(Y − B, G − max(R, B)) в уровнях RGB
  (BT.709, из U и V). Серый или чёрный дрон — смесь серого с цветом фона (дымка, цвет yuv420 вдвое реже
  яркости и размыт), его phi не больше max(0, phi фона), поэтому мерится превышение: leaf = phi тела −
  max(0, phi фона), с цветом листвы — при leaf ≥ 8. Фон — медианы яркости и цвета ~30 отсчётов кольца
  в 2–3.5 радиуса тела вокруг кандидата; если больше половины отсчётов кольца на фон не похожи (кромка
  крон), цвет не мерится. Тело — отсчёты в круге (k·pool/2 + 2) пикс. на уровне пирамиды, отклонённые
  от фона в сторону цели не меньше половины самого сильного: на облаке с голубыми просветами просветы
  темнее облака и иначе окрашивали бы тело в голубой. Трек, у которого среди последних 32 замеров
  цвета два с цветом листвы, — лист до конца: не захватывается, захват с него снимается сразу, в карту
  помех он не идёт. Окно — чтобы редкие случайные попадания за минуты ведения дрона не складывались.
  Цвет мерится только у кандидатов в прогнозах треков, которые можно захватить (не помех и не листьев):
  кандидатов на облаках и в кронах бывает за сотню. Цвет кадра приложение берёт отсчётом на блок 4x4 в
  его углу (`ColorPlanes`), `dronolok_bench` из y4m — так же: каждый второй отсчёт — в центре блока 8x8,
  как раньше, и маска неба бит в бит та же (мультитест с `leaf_color` = 0). Цвет с камеры yuv420
  (шаг 2) тело читает через 4 пикс. C API и Python — без цвета, как и облака по цвету.

  все сдвиги такта) — wt23 1.1% то же, wt15 жёсткий на дроне 81.0 → 84.8%, ложный захват 1.70 → 1.42%,
  wt17 захват на дроне 86.0 → 85.5% (на одном сдвиге захват, снятый с листа, перешёл на другую ложную
  цель и дольше её держал), в среднем по дронам 90.4% то же. На самом дроне (ближе 12 пикс. к
  разметке) из 1068 замеров цвета ни одного с цветом листвы: наибольшее leaf 5.6, 99% не выше 3.7.
  Остаются лист на фоне тёплого, освещённого солнцем облака (его phi почти как у облака) и лист, от
  которого отстал трек. Риск — дрон хаки или оливковый на солнце вблизи: он окрашен, как листва (тогда
  галочку снять). Цена (1 поток x86, 2560x1440): 2–3 мкс на кандидат, на кадр до 0.04 мс, а где камера
  ведёт дрон и живых треков 40–150 (wt15–19) — 0.1–0.35 мс. Выборка цвета в декодере приложения с
  шагом 4 — 0.7 мс на кадр 2560x1440 (с шагом 8 было 0.25), в потоке декодера параллельно обработке.
- **Доросшая маска открывается обратно** (`reopen_quiet` = 0.9): тайлы, закрытые доращиванием,
  считаются на кадрах перепроверки; если ни одна ячейка закрытой полярности не дотягивает до порога в
  90% замеров за ~2*`recheck_frames` кадров (облако ушло, помехам неоткуда взяться), тайл открывается.
  На роликах (6–30 с) тайлы затихнуть не успевают, захват и ложные те же.
- **Цель в захвате ищется и под маской** (`lock_through`, `lock_through_k` = 1.5): дрон, залетевший в
  закрытый тайл (облако, кромка), раньше пропадал. В круге прогноза захваченного трека
  (`Tracker::lockSearch`) ячейки под маской смотрятся с порогом x1.5; кандидат берётся, только если
  он той же полярности, его контраст в пределах x2 от контраста трека и пятно в круге одно (два
  разных — неоднозначно, трек держится на прогнозе). Кандидат слабый: продолжает трек, новых не
  рождает. Включается только для летящей цели (ушла от точки рождения дальше 3*`mover_px`, не помеха,
  не птица, не на мачте): без этого условия держался и ложный захват (n2: жёсткий 12 → 22%). На роликах
  дрон под маску не залетает — захват на дроне тот же, ложный захват wt24 94.0 → 93.2%.
- **Менее важное небо** (вкладка «Вид», «менее важное небо»): фиолетовым — небо выше полосы у
  горизонта (её детектор смотрит раз в `upper_every` кадров), а без полосы — верхние 30% неба над
  землёй в каждом столбце (была половина: выглядело, будто полнеба не смотрим). Без полосы подсветка
  только показывает, поиск там тот же.
- **Зависшая цель уступает захват сильнее** (вес x0.05 вместо x0.2): точка в кроне, к которой
  перешёл трек пролетевшей цели, на записях War Thunder держала захват; ложный захват 38% → 30%,
  захват на цели 44% → 51%.
- **Листва на кромке** (`TrackerConfig::edge_mover_k` = 3): трек, родившийся у кромки, считается
  летящей целью, только пройдя втрое больше `mover_px` — крона на ветру «ходит» на десяток пикселей.
- **Жёсткий захват не слепит**: между редкими полными просмотрами кадра детектор смотрит вокруг
  всех живых треков (кроме помех), а не только вокруг захваченного — иначе второй дрон рядом с
  захваченной целью не набирал попаданий и не находился вовсе.

- **Кого захватывать** (`lock_slow` = 1, `hard_switch` = 2; галочка «захват: сначала мелкий
  медленный дрон»): вес для захвата делится на 1 + скорость / `lock_slow`, растёт с пробегом до 64
  пикс., у зависшей цели x0.05, и зависшая не держит жёсткий захват (иначе трек, перешедший с
  пролетевшей цели на неподвижную точку в кроне, держал его до конца ролика). Жёсткий захват
  переходит на цель вдвое весомее и вдвое медленнее (на просто более яркую — нет). Записи War Thunder: дроны в захвате 31% → 47%, самолёты и
  вертолёты 53% → 45%, ложный захват 26% → 26% кадров. Ограничение контраста в весе (`lock_cmax`)
  пробовали — хуже (ложный захват 47%).
- **Захват не скачет** (`lock_dwell` = 12 кадров при 25 к/с): вес двух далёких медленных целей
  колеблется в противофазе (мерцание, скорость у порога зависания), и захват перескакивал между
  ними каждые полсекунды. Теперь претендент должен быть весомее большую часть `lock_dwell` кадров.
  War Thunder wt10 (самолёт и дрон): смен цели 40 → 3, захват на дроне 83% → 100%, ложный 18% → 1%;
  по всем 14 роликам смен цели 493 → 136, на wt1–6 захват на цели 51% и ложный 29–30% — как было.

  Записи War Thunder (2560x1440, 60 к/с, неподвижная камера; 6 роликов, 14 летящих целей —
  самолёты, вертолёты, дроны 5–19 пикс.; правда — разность кадров на небе, `--bench`, 1 проход):
  обнаружение 49% → **95%**, захват на цели 19% → **46%**, ложных целей на кадр 8.0 → **1.9**,
  ложный захват 59% → **26%** кадров. Синтетика горизонта (`synth_horizon.py`, 4 и 16 Мп) — без
  изменений.
- **Ячейки 16x16** — бэкенд считает максимум отклика каждой ячейки (8x8 после пулинга) и его место.
- **Два кандидата в тайле** (`per_tile = 2`, по умолчанию): второй — сильнейшая ячейка вдали от первого.
  Пара дронов в 20 пикс.: 65% → 99%.
- **Фон по ячейкам у кромки** (`bg_map`, по умолчанию): маска не расширяется на тайл запаса, текстурные
  тайлы у земли смотрятся по ячейкам с порогом медиана + `bg_k`·СКО максимума ячейки (скользящие
  квантили за `bg_frames` кадров), шум неба для общего порога — без них. Дальние дроны: 16% → 52%
  (облачно: 1% → 14%), ложных не прибавилось. Порог по ячейке на всё небо пробовали — хуже (52% → 6%):
  на ровном небе общий порог по шуму точнее.
- **Накопление** (`tbd`, выключено): track-before-detect на ячейках. Пока не окупается: на 16 Мп
  дальних 19% → 28%, но на сценах 4 Мп прироста нет, а ложных +10..70 в минуту; дрон с контрастом 7-12
  не находится и с ним — максимум по ячейке 16x16 сам шумит. И +4.7 мс на 16 Мп.
- **Полоса у горизонта** (`band_px`, `upper_every`): полоса над кромкой земли — каждый кадр, небо
  выше — раз в N кадров (и вокруг треков). 16 Мп, полоса 512: раз в 2 — без потерь; раз в 3 —
  ещё быстрее, но высокие цели 97% → 90%. Пониженный порог в полосе (`band_k` < 1) вреден.

|---|---|---|---|---|---|

## Точность: сетка сложности

Синтетика прямо в памяти (2048x1024, гауссово пятно FWHM 1–8 пикс. с субпиксельным положением,
контраст 4–50 уровней, шум матрицы σ 1–8, скорость 0–12 пикс./кадр, фон: небо, облака, кромка
леса на ветру; 150–250 кадров на точку) и записи War Thunder wt4, wt6–wt14. Что нашлось и что
изменилось:

- **Крупная цель — не текстура** (`DetectorConfig::compact_tex`, по умолчанию). Близкий контрастный
  дрон (FWHM 5+ пикс., контраст 30+) сам набирает «горячих» пикселей больше `max_density`, его тайл
  считался текстурой и цель пропадала: FWHM 6, контраст 30 — найдено 29% кадров, контраст 50 — 18%.
  Теперь тайл, где все горячие ячейки 16x16 собраны вокруг максимума (3x3 ячейки), не текстура:
  93% и 93%. У земли (тайлы рядом с маской) правило не действует — там так же выглядит верхушка
  дерева; маска неба учится по прежнему признаку. Ложных на синтетике без целей не прибавилось.
- **У кромки — только прямой полёт** (`TrackerConfig::edge_straight` = 0.5). Трек, родившийся у
  кромки крон, выдаётся, только если путь за последние до 48 попаданий (8 отрезков) прямой хотя бы
  наполовину: смещение / длина пути. Листва на кромке за минуты набирает `edge_mover_k` пробега,
  но ходит туда-сюда (прямота ~0.4), дрон летит прямо (0.9+). Вместе с `compact_tex` на записях
  War Thunder: полнота 65.5% → 67.8%, ложных треков на кадр 8.6 → 7.9; синтетика горизонта
  (`synth_horizon.py`) не изменилась, на `synth_sky.py --cls` полнота та же, ложных тревог +1 за 32 с.
- **Положение точнее пикселя** (`subpixel`, выключено): центр кандидата основного масштаба — вершина
  пятна на сглаженном 3x3 кадре (гаусс по трём точкам вдоль x и y). Ошибка положения 0.8 → 0.1–0.3
  пикс., обнаружение то же. Для наведения узкой камеры и поворотки.
- **Сглаживание 3x3** (`smooth`, `smooth_k` = 0.5, выключено): кадр сглаживается [1 2 1]x[1 2 1]
  перед пулингом (SIMD, точно по формуле), порог — `thr * smooth_k`. Это согласованный фильтр для
  точки 2–4 пикс.: на белом шуме контраст, при котором цель находится в половине кадров, для FWHM
  2.5 — 12.2 → 7.9, ложных столько же. Но резкие точки в 1 пикс. видно хуже (23 → 25), а широкие
  пятна облаков проходят половинный порог — поэтому `smooth_compact`: пятно шире ~3 пикс.
  (амплитуда в 2 пикс. от пика больше 0.45 от пика) должно пройти порог как без сглаживания. На
  записях War Thunder (резкая графика) и `synth_sky.py --cls` полнота со сглаживанием ниже — потому
  выключено; проверять на своей камере (мультитест, ключ `smooth`). Цена: кадр 2280x1440 на 4 потоках
  AVX2 — 1.7 → 2.4 мс.
- **Новая точка в спокойном небе** (`TrackerConfig::quiet_frames`, выключено; 50 — 2 с). Дрон, который
  висит или летит прямо на камеру, по кадру почти не движется, и карта клаттера гасит его за ~15
  кадров: на синтетике при скорости 0 и 0.3 пикс./кадр трек выдаётся в 1–15% кадров. Трек,
  родившийся там, где `quiet_frames` кадров не было откликов (камера стоит, вокруг на `quiet_r`
  пусто), карту не греет и правилом пробега не гасится: 50–74%. Появился сосед (кромка облака,
  листва) — флаг снимается; через `quiet_max` кадров — обычная помеха. Ложных на сетке не
  прибавилось, но на `synth_sky.py --cls` ложных тревог 9 → 24 в минуту; на wt9 выдал 7 неподвижных точек в верхнем небе (похоже, дальние самолёты — в
  разметке неподвижных целей нет).
- **Шумная матрица.** С постоянным порогом (`thr` 10) при σ ≥ 3.5 детектор слепнет полностью: все
  тайлы — «текстура», нет даже цели с контрастом 40. При σ 3 — 93 ложных кандидата на Мп. С порогом
  по шуму (`auto_thr`) деградация плавная (контраст 40: σ 5 — 98%, σ 6 — 72%), ложных ~0. На ровном
  небе `auto_thr` опускает порог до `thr_min` = 5, что на wt9 мешало захвату: для «только вверх»
  ставьте `thr_min` = `thr`. Подстройка под сцену сама включает `auto_thr` при шуме неба > 2.6 — как раз
  перед обрывом. Со сглаживанием предел дальше: контраст 20, σ 4 — 99% кадров вместо 17%.

`dronolok_bench --gt` пишет и полноту детектора до трекера («кандидаты детектора ближе 6 пикс.»,
`cand_recall_drone` в JSON) — видно, кто потерял цель: детектор или трекер.

## Подстройка под сцену и погоду (`dronolok/scene.hpp`)

`SceneAnalyzer` раз в ~0.2 с смотрит разреженную выборку кадра (~60 тыс. точек, блоки 4x4 точки;
0.6 мс на анализ на 4 Мп, т.е. ~0.1 мс на кадр) и оценивает:

- **свет** — яркость неба и шум матрицы: день / сумерки / ночь, пересвет;
- **погоду** — облачность, качание кромки леса на ветру (сдвиг крон в пикселях), осадки (точечные
  вспышки на небе, снег даёт их вдвое больше дождя), дымку (кромка и земля почти как небо);
- **окружение** — кромку земли по столбцам (текстура или заметно темнее неба над ней), долю неба,
  тип того, что ниже горизонта: лес (рваная кромка), город (ровные отрезки крыш на разной высоте),
  поле (ровная и низкая);
- **перемены** — скачок яркости неба за ~1 с (облако закрыло солнце) и сдвиг сцены (кромка ушла или
  узор земли не совпал с опорным — камеру повернули).

`scene_profile()` подстраивает выставленные настройки детектора и трекера (плавно, по сглаженной
оценке): сумерки, ночь, дымка, шумная матрица — порог по шуму; ночь — только светлые цели (огни);
снегопад днём — только тёмные; осадки — строже подтверждение трека; ветер — цель, родившаяся у
кромки, должна пролететь дальше (`edge_mover_k` 1.5…4), в штиль выдаётся раньше; город — память
неподвижных помех учится быстрее. Скачок света — `Detector::resetBackground()`; сдвиг сцены или смена
порога/полярности — маска неба учится заново. В приложении — галочка «Подстраиваться под сцену и
погоду» (вкладка «Алгоритм», по умолчанию включена), состояние сцены — справа на вкладке «Цели».
`dronolok_bench --scene` / `--adapt` / `--scene-log out.csv`.

Стенд: `detector/synth_horizon.py --scene city|field --light dusk|night --rain 1 --snow 1 --fog 0.5
--change-at 5 --change-gain 0.6 ...` (4 Мп, 10 с, маска учится на первых 25 кадрах, оценка — второй
проход). Все 12 сцен опознаны верно. Дроны найдены, % / ложных тревог в минуту, без подстройки → с ней:

| сцена | без | с подстройкой | что подстроено |
|---|---|---|---|
| день, лес / штиль / ветер / город / поле | 45–59% / 0 | то же | ветер, город |
| сумерки (шум 3.5) | 0% / 0 | **28%** / 0 | порог по шуму |
| ночь, дроны с огнями | 0% / 0 | **20%** / 0 | только светлые, порог по шуму |
| дымка 50% | 14% / 0 | **22%** / 0 | порог по шуму |
| дождь | 42% / 78 | 42% / **36** | строже подтверждение |
| снег | 44% / 45 462 | 36% / **0** | только тёмные (светлый дрон в снег не виден) |
| гроза посреди ролика | 45% / 54 | 45% / 48 | строже подтверждение |
| облако закрыло солнце | 38% / 0 | 38% / 0 | фон заново |

Записи War Thunder (правда — `detector/motion_truth.py`, разность кадров на небе): wt4 (первые 20 с)
камера переключалась при старте, подстройка заметила сдвиг сцены и выучила маску заново: целей
найдено 11 → 14 из 18, доля кадров с целью 29% → 58%, ложных тревог 1128 → 1555 в минуту (открылось
больше неба). wt6 (штиль) — без изменений (67%, 584 → 581 в минуту). Дальние тусклые дроны (контраст
7–12) не находятся ни так, ни так — это не погода, а порог детектора.

Пока не умеет: панораму 360° (оценка — для одного направления камеры), цвет (кадр серый; синий
канал помог бы в облаках), отличать дождь от снега иначе как по числу вспышек.

## Подстройка под железо (`dronolok/tuning.hpp`)

Алгоритм собран из блоков, которые можно включать и выключать под устройство: масштабы (крупные
близкие цели), учёт движения камеры, зоны кадра, тёмные и яркие цели, маска неба, память помех,
экономия (весь кадр и крупные масштабы раз в N кадров), разрешение обработки.

- `profile_blocks(Profile)` + `apply_blocks()` — готовые наборы: Полный, Сбалансированный (по умолчанию),
  Экономный (Pi 4–5), Минимальный (Pi 3: только точки и тёмные цели, кадр вдвое меньше).
- `LoadGovernor` — держит обработку в темпе камеры. Каждый кадр `update(мс кадра, период камеры)`; когда
  среднее время выше 90% периода, упрощает на ступень (1: крупные масштабы раз в 2 кадра, 2: весь кадр
  раз в 2, 3: крупные раз в 4, 4: весь кадр раз в 3 и до 2 масштабов, 5: раз в 4 и 1 масштаб), когда
  ниже 50% — возвращает. `LoadGovernor::apply(level, cfg)` + `Detector::reconfigure(cfg)`.
- `calibrate_ms_per_mp()` / `dronolok_bench --calibrate` — эталонный замер ядра: мс на 1 Мп, 1 поток,
  128-битный SIMD. Отношение чисел устройства и ПК — во сколько раз растянуть обработку при имитации
  устройства в приложении. Xeon 2.8 ГГц: ~0.6; Pi 5 / 4 / 3 — пока оценки 1.5 / 3.5 / 9, точное число
  даст запуск на устройстве.

## Дрон или птица

Классификатор (`Tracker::classify`, пороги в `TrackerConfig`) смотрит на характер движения трека:

- **Рваная траектория.** Отклонение от плавной параболы за последние 16 попаданий: ласточка дёргается.
- **Взмахи крыльев.** Детектор для каждого кандидата считает суммарный контраст пятна (`Candidate::energy`,
  окно 5x5 вокруг самого тёмного пикселя минус фон рамки). У точки в 1–4 пикс. он следует за площадью
  силуэта, то есть за крыльями. Трекер за последние 48 кадров убирает из него тренд и ищет синусоиду с
  периодом 2–16 кадров (при 25 кадр/с — 1.5–12.5 Гц; более частые взмахи складываются в эти же частоты).
  Птица, если синусоида объясняет не меньше 60% дисперсии (`flap_r2`) и размах пульсации не меньше 30%
  среднего. Было 45%: на 14–15 к/с окно взмахов — 32 кадра, и медленное колебание контраста дрона в дымке
  объясняло 45–50% — «птица», жёсткий захват снят (wt25 на 15 к/с −10 пунктов). Цена на синтетике ниже
  (25 к/с): «птица» у попаданий по птицам 65 → 63%, у дронов без изменений.
  Около 40 частот x 48 точек, косинусы поворотом: на 1080p трекер 0.1 → 0.3 мс на кадр при ~25 треках.
- **Память.** Махавшая птица остаётся птицей ещё 50 кадров: воробьиные машут пачками и планируют.
- **Стая.** Попутчик машущей птицы (ближе 150 пикс., скорость отличается меньше чем на 35%) — тоже птица.
  Рой дронов крыльями не машет и так не помечается.
- **Зависание.** Летала, а теперь стоит — дрон (если не машет).

Синтетика `synth_sky.py --cls` (1920x1080, 400 кадров): птицы летят ровно, по траектории их не отличить,
и машут 2–15 Гц, часть — пачками; стая из 5; чайка кружит без взмахов; дроны зависают и разворачиваются.
Доля кадров с классом «птица»:

| Цель | Без взмахов | Со взмахами и стаей |
|---|---:|---:|
| ровно машущие птицы (8, из них 5 в стае) | 52% | 88% |
| машущие пачками с планированием (3) | 11% | 12% |
| парящая чайка без взмахов | 0% | 0% |
| птицы с рваной траекторией (3) | 98.5% | 98.5% |
| дроны (8, из них 4 зависают) | 2.1% | 2.3% |

Машущих пачками пока узнаёт плохо: пачка в 0.4–1 с слишком коротка для уверенного периода. Парящую
птицу по движению не отличить от самолётного дрона. Основная синтетическая сцена (`synth_sky.py` без
`--cls`) не изменилась. Настройка: `dronolok_bench --dump-tracks` пишет признаки треков по кадрам
(`flap_r2`, `flap_period`, `flap_depth`, `energy`), флаги `--flap-window`, `--flap-r2`, `--flap-depth`,
`--flap-hold`, `--hover`, `--flock`.

## Из Python

```python
from dronolok_native import NativePointDetector, NativeTracker   # native/python/
det = NativePointDetector(threads=4)      # тот же интерфейс, что у detector.PointDetector
cands = det.detect(gray_frame)
trk = NativeTracker(gray_frame.shape)
tracks = trk.update(cands)
trk.queue(), trk.locked()                 # очередь целей по весу и захваченная
trk.next_target()                         # захват на следующую цель очереди
```

`detector/run_demo.py --native` прогоняет демо на нативном ядре.

## GPU и NPU

Вычисления спрятаны за интерфейсом `Backend` (`src/backend.hpp`): детектор отдаёт кадр и получает
статистику тайлов, всё остальное (выбор кандидатов, трекер) общее. Сейчас есть CPU-бэкенд. Следующие:

- **Vulkan compute** для GPU Raspberry Pi 5 (VideoCore VII, драйвер v3dv) и ПК. Морфология и статистика
  тайлов хорошо ложатся на шейдеры; главный вопрос на Pi — копирование кадра в GPU, нужен импорт
  DMA-буфера камеры без копии.
- **NPU** (Hailo-8L в AI Kit для Pi 5 и подобные) рассчитан на нейросети, а не на морфологию. Его место —
  второй шаг: классификатор дрон/птица по вырезкам 32x32 вокруг треков, которые уже нашёл этот детектор.
