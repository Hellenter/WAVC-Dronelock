# native/ — нативное ядро детектора (C++17, SIMD)

Тот же алгоритм, что в [`detector/`](../detector/), переписанный на C++ без OpenCV. На одном масштабе
(`scales = 1`) кандидаты совпадают с Python-версией бит в бит (проверка: `python/compare_with_python.py`).
Сверх прототипа: поиск крупных целей на уменьшенных копиях кадра, учёт движения камеры, трекер с
прогнозом (фильтр Калмана) и удержанием захвата.

## Что внутри

| Часть | Файлы | Что делает |
|---|---|---|
| Детектор | `src/detector.cpp`, `src/backend_cpu.cpp` | пулинг 2x2, морфологическое закрытие линиями в 4 направлениях, статистика тайлов 32x32, выбор кандидатов, авто-маска неба |
| Ядра SIMD | `src/kernels_*.cpp`, `src/simd.hpp`, `src/kernels_impl.hpp` | один шаблонный код под AVX2 (256 бит), SSE2 и NEON (128 бит) и скалярный эталон; набор выбирается при запуске по CPU |
| Потоки | `src/thread_pool.cpp` | кадр режется на блоки тайлов, блоки раздаются потокам; можно закрепить потоки за ядрами |
| Масштабы | `src/detector.cpp` | `scales` 2–4: тот же поиск на кадре, уменьшенном в 2, 4, 8 раз (min/max-пулинг) — цели до ~28, ~56, ~112 пикс. вместо ~7 |
| Движение камеры | `src/motion.cpp` | сдвиг картинки между кадрами: пирамида градиентов ~300 пикс., поиск минимума разности, субпиксель; ~1–2 мс |
| Трекер | `src/tracker.cpp` | фильтр Калмана (позиция + скорость), прогноз с учётом сдвига камеры, окно поиска по неопределённости прогноза, удержание трека и захвата на пропусках; классы дрон / птица / статичная помеха; одиночные отклики — шум |
| API | `include/dronolok/detector.hpp`, `include/dronolok/dronolok.h` | C++ и C (для Python/ctypes и других языков) |
| Инструменты | `tools/dronolok_bench.cpp`, `tests/test_kernels.cpp` | замеры, качество по разметке, сверка SIMD со скалярным кодом |

Почему так быстро: кадр обрабатывается полосами по нескольку строк, и все промежуточные данные (пулинг,
4 направления дилатации) живут в кольцевых буферах, которые помещаются в кэш L1/L2. В OpenCV каждый шаг
проходит по всему кадру 16 Мп и упирается в память. Плюс полностью замаскированные тайлы (лес, земля)
не считаются вовсе.

## Скорость, кадр 4608x3456 (16 Мп), мс на кадр

ПК: Xeon 2.8 ГГц, 4 vCPU (виртуалка). Python — `detector/` с OpenCV.

| Вариант | 1 поток | 4 потока |
|---|---:|---:|
| Python + OpenCV | 55–70 | 18–22 |
| нативное, скалярный код | 300 | 80 |
| нативное, SSE2 (128 бит, как NEON) | 15–20 | 4.5–6 |
| нативное, AVX2 (256 бит) | 10 | 3.5–4 |

Для Raspberry Pi ориентир — строка SSE2: NEON той же ширины. Ядра Cortex-A76 (Pi 5) примерно в 2–3 раза
медленнее ядра этого ПК, Cortex-A53 (Pi 3) ещё в 3–4 раза медленнее. Точные цифры даст `dronolok_bench`
на самом устройстве.

## Сборка

Нужны CMake 3.16+ и компилятор C++17 (GCC, Clang или MSVC).

```sh
cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build -j
native/build/test_kernels           # все SIMD-варианты совпадают со скалярным кодом
```

### Raspberry Pi

На самой Pi (Raspberry Pi OS, 64 или 32 бит) — те же команды. NEON включается автоматически.

Кросс-компиляция с ПК на Linux:

```sh
sudo apt install g++-aarch64-linux-gnu      # Pi 3/4/5 с 64-битной ОС
cmake -S native -B build-pi -DCMAKE_TOOLCHAIN_FILE=$PWD/native/cmake/aarch64-linux-gnu.cmake
cmake --build build-pi -j
# для 32-битной ОС: g++-arm-linux-gnueabihf и native/cmake/arm-linux-gnueabihf.cmake
```

Готовые сборки для Pi и Windows собирает GitHub Actions (`.github/workflows/build.yml`), они лежат в
артефактах запуска.

### Windows

Из Linux: `-DCMAKE_TOOLCHAIN_FILE=$PWD/native/cmake/mingw-w64-x86_64.cmake` (пакет `mingw-w64`).
На Windows: Visual Studio 2022, `cmake -S native -B build` и `cmake --build build --config Release`.

## Прогноз и захват

Трек хранит позицию и скорость цели относительно сцены (фильтр Калмана с постоянной скоростью). На каждом
кадре:

1. `GlobalMotion` оценивает, на сколько сдвинулась вся картинка (камера в руке); прогноз трека = прошлая
   позиция + скорость + сдвиг камеры.
2. Цель ищется в круге вокруг прогноза. Радиус — 4 сигмы ошибки прогноза: у молодого трека и после
   пропусков окно шире, у устойчиво летящей цели — уже (меньше шансов перескочить на соседнюю помеху).
3. Если цель не нашлась (слилась с фоном, ушла за провод), трек идёт по прогнозу до `max_miss` кадров.
   Новые и стоящие на месте треки так не держатся — иначе каждый блик оставлял бы «призрака».
4. Захват — самая весомая цель (контраст, число попаданий, не помеха). Он держится, пока трек жив, и
   переходит на другую цель, только если та весомее в `lock_switch` раз. Потерянный захват сначала ищется
   у прогноза и у последней известной точки.

5. **Память статичных помех** (неподвижная камера): места, где цели раз за разом появляются и никуда не
   летят (катушки и изоляторы ЛЭП, фонари), копят такие отклики. Набрав `static_hits` с забыванием за
   `static_frames` кадров, место перестаёт рождать цели; летящий через него трек не теряется.
   `Tracker::saveStatic/loadStatic` — чтобы после перезапуска не учиться заново. Синтетика 4 Мп с
   мерцающими катушками (`synth_sky.py --insulators 12`): ложных треков 2.1 → 0.3 на кадр, с сохранённой
   памятью 0.13; на синтетике 16 Мп 1.7 → 0.07; полнота та же.

6. **Зоны кадра** (`DetectorConfig::zones`): по тайлам основного масштаба — земля (крупные связные области
   текстуры: кроны, дома, край виньетки), небо и смешанные (небо рядом с землёй). Цель, родившаяся в
   смешанной зоне, выдаётся, только когда полетела. Считается каждый кадр, поэтому работает и при съёмке
   с рук. Ролики пользователя, целей на кадре (ложных в основном): большой дрон над домами 9.6 → 3.6,
   перехватчик над снегом 39.8 → 29.3 (ложные цели на ровном снегу зоны не убирают), дрон до взрыва
   5.0 → 4.6; захват тот же, синтетика 16 Мп без изменений.

7. **Порог по шуму** (`DetectorConfig::auto_thr`, по умолчанию выключен; CFAR, как в радарах и ИК-поиске
   малых целей). Шум отклика — медиана среднего отклика по тайлам кадра (лес и цели — меньшинство, медиана
   их не видит), сглаженная по кадрам; порог = `noise_k` x шум в пределах `thr_min`..`thr_max`, порог
   "горячих" пикселей (текстура, маска неба) — тоже от шума. Постоянный `thr = 10` подобран под шум матрицы
   ~2 уровня: на шумной матрице (вечер, высокий ISO) кадр засыпает ложными целями, а маска неба при обучении
   считает всё небо текстурой; на чистой — теряются тусклые дальние цели. Стоит медиана по ~4 тыс. тайлов
   (меньше 0.05 мс на 16 Мп).

8. **Подтверждение по накопленной уверенности** (`TrackerConfig::ev_confirm`, по умолчанию 3; упрощённый
   track-before-detect / последовательный тест отношения правдоподобия). Каждое попадание добавляет
   `margin^2 - 1`, где `margin` — во сколько раз отклик выше порога, пропуск отнимает 1. Трек выдаётся, когда
   выполнено прежнее "3 из 5" и набрано 3. Шумовые отклики у самого порога, случайно совпавшие 3 раза, больше
   не становятся целями; контрастная цель подтверждается так же быстро, как раньше, тусклая — на несколько
   кадров позже. Кандидаты не от `Detector` (через C API без `margin`) подтверждаются по-старому.

9. **Силуэт крупной цели** (`measure_silhouette`, `TrackerConfig::silhouette`, по умолчанию вкл.). У
   крупного БПЛА (100–400 пикс.) детектор точечных целей находит части: кончик крыла, хвост, подвес, — и
   захват цеплялся за одну из них. Вокруг прогноза захваченной цели (`Tracker::lockSearch`) берётся окно,
   уменьшенное до сетки не больше ~97x97 ячеек; фон и шум — по рамке окна, цель — связная область темнее
   (светлее) фона, расширенная на ячейку, чтобы тонкое крыло не рвало силуэт. Упирается в край окна — окно
   вдвое больше, до `silh_max` (больше — это земля или облако, не цель). Центр и габарит силуэта идут в
   трекер как измерение захваченной цели (`Tracker::setLockSilhouette`); части внутри габарита не рождают
   своих целей и не считаются помехой. Доли миллисекунды на кадр.

10. **Жёсткий захват** (`hard_lock`, `verify_frames` = 25, `hard_miss` = 60, `hard_full_every` = 6).
    Захваченная цель `verify_frames` обработанных кадров подряд классифицируется как дрон и уже пролетела
    по сцене — `LockState::Hard`: захват не переходит на другие цели, держится на прогнозе `hard_miss`
    кадров, детектор смотрит вокруг дрона (`Tracker::roi` только по нему), весь кадр — раз в
    `hard_full_every` кадров. Снимается, если цель оказалась наложением на кадр или уверенно птицей
    (`birdScore` > 0.8). Наложения на кадр (надписи записи экрана): позиция в кадре стоит на месте
    (СКО < `overlay_px` за `overlay_hits` попаданий), пока сцена смещается больше `overlay_cam`.
    Цель на мачте (`anchor_check`, по умолчанию вкл.): у силуэта захваченной цели ищется длинная тонкая
    линия вверх или вниз — мачта прожектора, столб, ствол (`Silhouette::attached`: линия от края силуэта
    длиннее цели в 2.5 раза, или узкий участок внутри силуэта длиннее ширины головы). В большинстве из
    первых 4+ замеров есть мачта — цель помеха, захват снимается. При съёмке с рук прожектор «летает» по
    кадру из-за неточной оценки поворота и проходил проверку на дрона: на ролике с перехватчиком захват
    сидел на прожекторе 243 кадра из 244, стало 31 (каждый новый трек на нём отпускается за 4 кадра).

    **Ожидание размера** (`size_predict`, по умолчанию вкл.): размер силуэта захваченной цели ведётся
    альфа-бета фильтром по логарифму — сам размер и скорость его изменения (`Track::ls/dls`,
    `Track::expectedSize()`), то есть приближается цель или удаляется. Детектор вокруг захвата смотрит на
    масштабе ожидаемого размера; силуэт больше ожидаемого в `size_tol` раз (слился с облаком, кроной) не
    принимается; меньший принимается, но в размер не идёт (крыло слилось с небом). Без замеров ожидание
    не экстраполируется: так оно расходилось с целью. Синтетика «крупный дрон пролетает мимо камеры»
    (62 → 400 → 62 пикс., `detector/synth_pass.py`): захват 95% → 98%; на роликах пользователя без изменений.

    **Камера ведёт цель** (`Tracker::setFollowing`, `Tracker::aim`): для камеры на поворотном
    устройстве, которая следует за захватом. `aim()` отдаёт позицию захваченной цели на кадре и её
    скорость по сцене — поворотке достаточно сдвинуть кадр на эту скорость плюс долю отклонения от
    центра. Поворот камеры передаётся в `update()` как `camDx/camDy` (от датчиков поворотки или
    `GlobalMotion`): цель стоит в кадре, а по сцене летит, фон едет навстречу — как доплеровский радар
    отделяет движущуюся цель от неподвижного фона. С `setFollowing(true)` захваченная цель не считается
    наложением на кадр (она и должна стоять в кадре, пока сцена уезжает), иначе захват снимался бы.
    Проверка — «виртуальная поворотка» в тест-приложении (`dronolok_app --follow`): алгоритм видит
    окно в половину кадра, окно поворачивается за проверенным дроном. На роликах пользователя (захват на
    дроне, 2-й проход; было → с поворотной камерой): крупный БПЛА 88% → **99%**, дрон-крыло у берёзы
    56% → **95%**, дальний дрон 40% → 42%, квадрокоптер в облаках 47% → 37–56% (по проходам), тяжёлый
    коптер 81% → 27% — без маски неба (у камеры на поворотке её нет) захватывается ведущий на правой
    половине записи экрана, у настоящей камеры такой вставки нет. Синтетика пролёта: пока цель в поле
    зрения окна, захват 100% кадров; классификатор при ведении увереннее (цель стоит на месте кадра, замеры
    стабильнее): доля «дрон» у захвата и время жёсткого захвата выше.

11. **Пробег цели по медиане**: точка рождения — медиана первых 5 отметок, текущая — последних 5. Одиночный
    скачок (силуэт пересчитал центр, детектор перепрыгнул на соседний отклик) больше не делает из
    неподвижного логотипа «летящую цель».

12. **Оценка движения камеры на записи экрана**: точки, не изменившиеся ни на уровень (наложения, повтор
    кадра), не учитываются; найденный сдвиг проверяется по 16 частям кадра — если за него меньше
    частей, чем вдвое против «сдвига нет», это шевелится что-то в кадре (ветки на ветру) при неподвижной
    камере, и сдвиг 0.

Ролики пользователя (запись экрана 2560x1440, 60 к/с с ролика 25–30 к/с), доля кадров с захватом на дроне по ручной разметке, 2-й проход (ложный захват):

Экономия (`DetectorConfig`): `coarse_every` (по умолчанию 2) — уменьшенные копии кадра целиком раз в N
кадров, между ними только если крупная цель уже ведётся: 16 Мп с 3 масштабами 7.4 → 5.7 мс. `full_every`
(по умолчанию 1) — основной масштаб целиком раз в N кадров, между ними только вокруг треков
(`Tracker::roi` → `Detector::setRoi`): 16 Мп 3.4 → 2.2 мс при 2, полнота 96.7% → 95% (новая цель находится
на кадр позже). Для Raspberry Pi.

Дополнительно (выключено по умолчанию): `Detector::setFocus` снижает порог детектора там, где трек ожидается
на следующем кадре; такие слабые отклики продолжают трек, но не рождают новые.

## Подстройка под железо (`dronolok/tuning.hpp`)

Алгоритм собран из блоков, которые можно включать и выключать под устройство: масштабы (крупные
близкие цели), учёт движения камеры, зоны кадра, тёмные и яркие цели, маска неба, память помех,
экономия (весь кадр и крупные масштабы раз в N кадров), разрешение обработки.

- `profile_blocks(Profile)` + `apply_blocks()` — готовые наборы: Полный, Сбалансированный (по умолчанию),
  Экономный (Pi 4–5), Минимальный (Pi 3: только точки и тёмные цели, кадр вдвое меньше).
- `LoadGovernor` — держит обработку в темпе камеры. Каждый кадр `update(мс кадра, период камеры)`; когда
  среднее время выше 90% периода, упрощает на ступень (1: крупные масштабы раз в 2 кадра, 2: весь кадр
  раз в 2, 3: крупные раз в 4, 4: весь кадр раз в 3 и до 2 масштабов, 5: раз в 4 и 1 масштаб), когда
  ниже 50% — возвращает. `LoadGovernor::apply(level, cfg)` + `Detector::reconfigure(cfg)`.
- `calibrate_ms_per_mp()` / `dronolok_bench --calibrate` — эталонный замер ядра: мс на 1 Мп, 1 поток,
  128-битный SIMD. Отношение чисел устройства и ПК — во сколько раз растянуть обработку при имитации
  устройства в приложении. Xeon 2.8 ГГц: ~0.6; Pi 5 / 4 / 3 — пока оценки 1.5 / 3.5 / 9, точное число
  даст запуск на устройстве.

## Дрон или птица

Классификатор (`Tracker::classify`, пороги в `TrackerConfig`) смотрит на характер движения трека:

- **Рваная траектория.** Отклонение от плавной параболы за последние 16 попаданий: ласточка дёргается.
- **Взмахи крыльев.** Детектор для каждого кандидата считает суммарный контраст пятна (`Candidate::energy`,
  окно 5x5 вокруг самого тёмного пикселя минус фон рамки). У точки в 1–4 пикс. он следует за площадью
  силуэта, то есть за крыльями. Трекер за последние 48 кадров убирает из него тренд и ищет синусоиду с
  периодом 2–16 кадров (при 25 кадр/с — 1.5–12.5 Гц; более частые взмахи складываются в эти же частоты).
  Птица, если синусоида объясняет не меньше 45% дисперсии и размах пульсации не меньше 30% среднего.
  Около 40 частот x 48 точек, косинусы поворотом: на 1080p трекер 0.1 → 0.3 мс на кадр при ~25 треках.
- **Память.** Махавшая птица остаётся птицей ещё 50 кадров: воробьиные машут пачками и планируют.
- **Стая.** Попутчик машущей птицы (ближе 150 пикс., скорость отличается меньше чем на 35%) — тоже птица.
  Рой дронов крыльями не машет и так не помечается.
- **Зависание.** Летала, а теперь стоит — дрон (если не машет).

Синтетика `synth_sky.py --cls` (1920x1080, 400 кадров): птицы летят ровно, по траектории их не отличить,
и машут 2–15 Гц, часть — пачками; стая из 5; чайка кружит без взмахов; дроны зависают и разворачиваются.
Доля кадров с классом «птица»:

| Цель | Без взмахов | Со взмахами и стаей |
|---|---:|---:|
| ровно машущие птицы (8, из них 5 в стае) | 52% | 88% |
| машущие пачками с планированием (3) | 11% | 12% |
| парящая чайка без взмахов | 0% | 0% |
| птицы с рваной траекторией (3) | 98.5% | 98.5% |
| дроны (8, из них 4 зависают) | 2.1% | 2.3% |

Машущих пачками пока узнаёт плохо: пачка в 0.4–1 с слишком коротка для уверенного периода. Парящую
птицу по движению не отличить от самолётного дрона. Основная синтетическая сцена (`synth_sky.py` без
`--cls`) не изменилась. Настройка: `dronolok_bench --dump-tracks` пишет признаки треков по кадрам
(`flap_r2`, `flap_period`, `flap_depth`, `energy`), флаги `--flap-window`, `--flap-r2`, `--flap-depth`,
`--flap-hold`, `--hover`, `--flock`.

## Замеры: `dronolok_bench`

```sh
# видео -> серые кадры y4m -> замер (кадры загружаются в память заранее, чтение не мешает)
ffmpeg -i video.mp4 -frames:v 100 -pix_fmt gray -f yuv4mpegpipe sky.y4m
dronolok_bench sky.y4m --sweep                         # таблица: набор инструкций x потоки
dronolok_bench sky.y4m --threads 2 --isa sse2 --cpus 2,3
dronolok_bench sky.y4m --gt video.mp4.gt.json --learn-mask 25   # полнота, ложные треки, классы
dronolok_bench hand.y4m --scales 3 --motion                       # съёмка с рук, близкая крупная цель
dronolok_bench sky.y4m --full-every 2 --static 3000                # экономия для Pi, память помех
dronolok_bench sky.y4m --auto-thr --ev 3                         # порог по шуму, подтверждение по уверенности
# с камеры или из файла потоком, вместе с декодированием:
ffmpeg -i rtsp://... -pix_fmt gray -f yuv4mpegpipe - | dronolok_bench - --stream
```

## GPU и NPU

Вычисления спрятаны за интерфейсом `Backend` (`src/backend.hpp`): детектор отдаёт кадр и получает
статистику тайлов, всё остальное (выбор кандидатов, трекер) общее. Сейчас есть CPU-бэкенд. Следующие:

- **Vulkan compute** для GPU Raspberry Pi 5 (VideoCore VII, драйвер v3dv) и ПК. Морфология и статистика
  тайлов хорошо ложатся на шейдеры; главный вопрос на Pi — копирование кадра в GPU, нужен импорт
  DMA-буфера камеры без копии.
- **NPU** (Hailo-8L в AI Kit для Pi 5 и подобные) рассчитан на нейросети, а не на морфологию. Его место —
  второй шаг: классификатор дрон/птица по вырезкам 32x32 вокруг треков, которые уже нашёл этот детектор.
